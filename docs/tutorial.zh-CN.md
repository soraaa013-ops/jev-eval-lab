# Jev Eval Lab 实验讲解：用了什么数据、怎样评判、结果如何

这个项目想回答一个问题：**能不能让模型当“评委”，判断另一个模型的回答或操作是否正确？Jev 与普通 LLM 当评委，各有什么优势和不足？**

这里没有训练新模型。实验使用现成模型，设计它们要看的材料、要回答的问题和评分规则，再把它们的判断与数据集给出的标准标签比较。

先说主要结果：**评两段回答谁更好时，GPT-5 mini 更准，Jev 更快、更便宜；评真实 agent 的操作过程时，本轮 Jev 表现更好，但仍漏掉约三分之二的错误。** 所以，“Jev 能否当评委”的答案取决于具体评什么，不能只用一个总分决定。

## 1. 一共做了哪些实验？

项目的三组主要实验如下。本文先讲最贴近 agent 应用的第三组，再解释前两组。

| 实验 | 给评委看什么 | 让评委做什么 | 想弄清楚什么 |
|---|---|---|---|
| 回答二选一：JudgeBench | 同一道题的两份回答 | 选更好的回答；交换顺序再选一次 | 谁判断更准？会不会偏爱某个位置？ |
| 多回答评选：RewardBench 2 | 同一道题的多个回答 | 直接选最好，或者先逐个打分 | 同一个 Jev，换一种评法，结果会不会变？ |
| Agent 过程：AgentProcessBench | 用户要求、规则、工具和完整执行记录 | 给每个 assistant 步骤分类，并判断最终成败 | 谁能发现 agent 做错了什么？ |

“评委”与“被评对象”是两回事。例如，被评对象可能是一条早已生成的订票轨迹；Jev 和 GPT 只阅读记录、作判断，不会在这轮实验里真的替用户订票。

## 2. 主实验：模型能看出 agent 哪一步做错了吗？

### 2.1 为什么要做这组实验？

评一段回答，主要看回答内容。评 agent，还要把用户目标、执行动作和工具结果对应起来。

例如用户要求“在 workspace 里创建 Projects 文件夹”。工具返回创建成功，并不一定代表完成任务：如果建在 workspace 外面，操作成功了，任务却做错了。

因此，这组实验不只问“最后一句话说得好不好”，而是让模型检查整个执行过程。

### 2.2 数据从哪里来？一条数据是什么？

使用公开数据集 **AgentProcessBench（APB）** 中的 BFCL 与 tau2 两个完整子集：

| 数据 | 主要内容 | 轨迹数 |
|---|---|---:|
| BFCL | 多轮工具使用 | 250 |
| tau2 | 带业务规则的交互任务 | 250 |
| 合计 | 100 个底层问题，每题 5 条执行轨迹 | 500 |

这 500 条轨迹共有 **6,147 个带人工标签的 assistant 步骤**。它们是已有 agent 运行留下的记录，本项目没有重新运行那些 agent。

一条轨迹可以理解为一份完整的工作记录：

```text
用户想完成什么
业务规则是什么、有哪些工具可以使用
用户说了什么
agent 发起了什么工具调用
工具实际返回了什么
agent 根据返回结果继续做了什么
……直到结束
```

数据集还提供人工对各步骤的判断。**人工标签只用于最后算成绩，不给评委看。** 评委也看不到独立存放的参考答案和环境评分字段。

这里只选了工具使用与业务交互两个子集，不包含 APB 的 GAIA 和 HotpotQA，因此结果代表这次任务范围，不代表整个 APB。

### 2.3 怎样把一条轨迹变成评估任务？

评委阅读相同的用户任务、规则、工具定义和完整消息记录。**逐步评分指每步分别输出标签，不是每次只输入单次交互：评第 5 步时，前面的上下文和后续步骤都可见。**用户消息和工具返回是判断依据；需要打标签的是 assistant 消息，包括工具调用和文字回复。

每一步只能选三类之一：

| 标签 | 含义 | 例子（教学示意） |
|---|---|---|
| +1 | 正确，并推进任务 | 先查询当前目录，再选择正确目标路径 |
| 0 | 中性或合理探索 | 合理查询遇到外部服务故障；尚未造成错误的部分规划 |
| −1 | 错误或有害 | 用错参数、误读工具结果、违反规则、没有改进地重复失败 |

规则还处理“错误会不会传到后面”：如果后续行为依赖一个未纠正的错误，也应受罚；如果明确改正，或者后续步骤独立恢复了正常进展，可以重新判为正确。

**为什么保留 0？** 因为 agent 探索未知环境时，不是每个没有立即成功的动作都应算错。否则评委会把合理探索和真正失误混在一起。

### 2.4 Jev、Clef 和 GPT 分别怎么做？

这组实验比较 Jev 1.14、Clef-flash、GPT-5 mini。它们看到同样的执行材料，使用相同含义的评分规则，但输出方式不同：

| 模型 | 怎样给出判断 |
|---|---|
| Jev / Clef | 把每一步当成一道三选一题，返回类别和类别概率 |
| GPT-5 mini | 根据提示生成每一步的标签和简短解释 |

最后再附加一道二选一题：“整个任务完成了吗？”

举例来说，假设一条轨迹有 12 个 assistant 步骤，那么评委需要给出 12 个过程标签，加 1 个最终成败判断。**一条轨迹不是只评一个总分。**

Jev/Clef 使用预先定义的选项；GPT 用语言生成判断。固定选项能限定输出形式，但不保证判断正确。GPT 能解释理由，也不保证理由与事实相符。本实验最终比较的都是预测标签与人工标签是否一致。

GPT 本轮使用 low reasoning 和简短解释，因此结果对应这套预算设置，不能代表所有 GPT 模型或更高推理预算。

### 2.5 实验实际怎么跑？

每条轨迹分别交给三个评委，因此共有 **500 × 3 = 1,500 份轨迹评估任务**。

长轨迹可能超过决策接口一次允许的问题数，所以 Jev/Clef 每批最多提出 64 个问题。各批仍然看到完整轨迹，只把要回答的问题拆开。这没有删掉后半段证据，但重复输入会增加费用。

每份任务最多尝试三次。最终：

- Jev 完成 500 条。
- GPT-5 mini 完成 500 条。
- Clef 完成 497 条，3 条因输入长度限制而终止失败。

失败轨迹涉及的 264 个步骤预测没有被排除，而是在主成绩中按错处理。否则，模型只要在难题上不给答案，就可能虚高成绩。

### 2.6 怎样算成绩？为什么不只看正确率？

人工标签分布很不均衡：

| 人工标签 | 步骤数 | 占比 |
|---|---:|---:|
| +1 正确推进 | 4,236 | 68.91% |
| 0 中性探索 | 231 | 3.76% |
| −1 错误 | 1,680 | 27.33% |

因此，一个完全不读轨迹、每一步都猜 +1 的评委，也有 **68.91% 正确率**。但它一个错误都发现不了。

所以主要看四个指标：

| 指标 | 用普通话解释 | 方向 |
|---|---|---|
| 逐步准确率 | 所有步骤中，有多少标签与人工一致 | 越高越好 |
| 宏 F1 | 分别衡量三类识别能力，再给三类相同权重求平均 | 越高越好 |
| 错误召回 | 100 个真正错误中，找出了几个 | 越高越好 |
| 错误误报率 | 100 个正常或中性步骤中，错怪了几个 | 越低越好 |

宏 F1 的计算是：对每个类别分别算 precision（判成这一类的有多少是真的）和 recall（这一类有多少被找出来），用 `2 × precision × recall / (precision + recall)` 合成 F1，再平均三类 F1。这样少数类不会被大量的 +1 完全淹没。

### 2.7 结果怎么样？

| 评委 | 宏 F1 | 逐步准确率 | 每 100 个错误找出几个 | 每 100 个正常/中性步骤误报几个 |
|---|---:|---:|---:|---:|
| Jev 1.14 | **50.45%** | **77.13%** | **34.35** | 2.22 |
| Clef-flash | 42.45% | 66.15% | 16.79 | 2.08 |
| GPT-5 mini | 37.57% | 71.22% | 13.45 | **1.32** |
| 永远猜 +1 | 27.20% | 68.91% | 0 | 0 |

这张表可以分三层读：

**第一，Jev 在本轮过程判断中最好。** 三类平均能力、总准确率和发现错误的能力都领先。

**第二，GPT 的总准确率高于 Clef，但宏 F1 更低。** 总准确率容易受到数量最多的正向步骤影响，不能单靠它给三分类评委排名。

**第三，三个模型都漏掉大量错误。** Jev 每 100 个错误只能找出约 34 个，仍漏掉约 66 个。它比另外两个模型好，不等于足够可靠。

Jev 相对 GPT 的宏 F1 高 12.88 个百分点。考虑样本波动后，差值的 95% 区间为 9.10—16.41 个百分点。计算时把同一问题的五条轨迹放在一起抽样，因为它们相关，不能把 6,147 个步骤当作 6,147 个独立任务。

只看三个评委都成功完成的 497 条轨迹，宏 F1 仍是 Jev > Clef > GPT。因此排名并不只是 Clef 接口失败造成的。

### 2.8 判断最终成功，和发现过程错误，是一回事吗？

不是。一个任务可能中途犯错后修正，也可能多数步骤正确、最后仍未达成目标，所以另外统计最终成败判断。

数据中有 20 条终局标签是中性，而本轮终局问题只允许成功/失败。因此下面的二分类成绩只用另外 **480 条**；过程评价仍使用全部 500 条。

| 评委 | 最终成败判断准确率 | 整轮报告费用 | 每条轨迹耗时中位数 |
|---|---:|---:|---:|
| Jev | **76.04%** | $0.3414 | **0.57 秒** |
| Clef | 58.96% | **$0.1764** | 1.12 秒 |
| GPT-5 mini | 64.17% | $2.3014 | 8.93 秒 |

费用包含有费用记录的失败和重试；耗时包含该轨迹的分批与重试。费用表仍是整轮 500 条的费用，不是只给 480 条计算费用。

本轮 Jev 比 GPT 更准、更快、更便宜；Clef 的费用更低，但判断质量也更低。

### 2.9 用一个真实案例理解结果

在 BFCL 的一条轨迹中，用户要求在 `workspace` 里面创建 `Projects`：

1. 工具报告当前目录为 `/alex`。
2. agent 没有进入 workspace，就创建了 Projects。
3. 列目录结果显示 workspace 与 Projects 并列。
4. agent 仍告诉用户已经完成。

| 被评步骤 | 人工标签 | Jev | Clef | GPT |
|---|---:|---:|---:|---:|
| 在错误位置创建 Projects | −1 | −1 | +1 | +1 |
| 随后宣称完成任务 | −1 | +1 | +1 | +1 |

Jev 看出了创建位置错误，却没有稳定地把错误传递到后面的成功声明。这就是“能发现部分局部错误，但还不能可靠检查整个过程”的具体表现。

这个案例用于解释问题，整体排名来自全部样本。

### 2.10 这组实验没有证明什么？

它测的是**看完完整记录后，能不能判断对**。评委实际看到了未来步骤，即使评分规则要求只依据当时信息，也仍可能受到后见之明影响。

它没有把评委接到正在运行的 agent 中，也没有测“提醒后能否纠错、任务成功率提高多少”。因此，不能把本轮成绩直接翻译成上线后的收益。

## 3. 回答二选一实验：谁更会挑正确答案？

### 3.1 数据怎么设计？

使用 JudgeBench 的 GPT-4o 回答子集，共 **350 道回答对**，包含知识、推理和代码相关问题。

每条数据有三个部分：原问题、回答 A、回答 B；数据集提供哪份回答更好的标签。这里的 GPT-4o 指候选回答的来源，本项目实际比较的评委是 Jev、GPT-5 mini、Qwen 和 Skywork reward model。

以下只是说明格式的简单例子，不是真实难度：

```text
问题：2+2 等于多少？
回答 A：4。
回答 B：5。
标准标签：A。
```

评委看问题和两份回答，判断哪个更正确，而不是重新生成一份答案。

### 3.2 为什么每题要评两次？

同一道题再交换候选位置：

```text
第一次：A=4，B=5，应该选 A。
第二次：A=5，B=4，应该选 B。
```

如果模型真正按内容选，字母应该改变，但选择的内容不变。如果一直偏爱左边、第一项或 A，就会暴露出来。

因此，每个托管评委做 **350 × 2 = 700 次判断**。

三项核心成绩是：

- **逐次准确率**：700 次里选对多少次。
- **双顺序都正确**：350 道题里，两次都选对的有多少道。
- **顺序一致率**：交换位置后，仍选同一份回答的有多少道；选错内容也可能保持一致。

一个永远选 A 的模型，在这套设计下能拿 50% 逐次准确率，但“双顺序都正确”为 0。这正是不能只测一个顺序的原因。

### 3.3 四个模型怎样完成任务？

Jev 直接做 A/B 选择，并给出概率。GPT 和 Qwen 根据提示生成 A/B 标签与自报概率。三者都看到同一题和同一对候选。

Skywork 的机制不同：分别给两份回答打分，再选择分数高的一份。交换顺序时直接交换已有分数，因此它的顺序一致率天然是 100%，不是额外学会了抵抗位置偏差。

本轮 Skywork 只使用 256 tokens 的上下文上限，会截掉长输入中的部分内容。这是资源受限的本地对照，不代表它完整上下文下的最佳表现。

### 3.4 结果怎么样？

| 评委 | 逐次准确率 | 双顺序都正确 | 顺序一致率 | 单次耗时中位数 | 该轮报告 API 费用 |
|---|---:|---:|---:|---:|---:|
| GPT-5 mini | **85.71%** | **80.57%** | 89.71% | 14.16 秒 | $2.3001 |
| Jev 1.14 | 78.14% | 70.57% | 84.86% | **0.436 秒** | **$0.0543** |
| Qwen3-30B-A3B | 64.29% | 40.00% | 51.43% | 1.19 秒 | $0.1128 |
| Skywork 0.6B，短上下文 | 60.29% | 60.29% | 100%（机制决定） | 10.28 秒 | 本地推理，无 API 费 |

这组结果与 agent 实验不同：**GPT 更准确，Jev 以较低准确率换取速度和费用优势。** Jev 比 GPT 低 7.57 个百分点，费用约为其 1/42，单次耗时中位数约为其 1/32。

Qwen 的双顺序都正确只有 40%，明显低于其逐次准确率，说明位置变化对判断影响很大。Skywork 的一致性最高，但准确率最低；一致性不等于正确。

本地推理没有 API 账单，不代表计算资源免费，其耗时也受本机硬件影响。

### 3.5 模型说“我有九成把握”，能相信吗？

实验还考察概率质量。这里要区分两个问题：

- 选得准不准：看准确率。
- 把握是否符合实际：看概率与真实正确情况是否匹配。

例如，模型对 100 次判断都说有 90% 把握，但只对了 60 次，就明显过度自信。

项目计算了概率平方误差（Brier）与分箱校准误差（ECE）。Jev 的 ECE 为 0.0410，GPT 为 0.0715；GPT 的 Brier 为 0.1055，优于 Jev 的 0.1439，两项都是越低越好。

这说明“概率是否校准”和“预测是否准确”并不是同一个维度。概率指标的结果也不能直接推导出其它任务上的可靠阈值。

## 4. 多回答实验：直接选最好，与先打分再选，有什么区别？

### 4.1 为什么加做这组实验？

实际评估经常不是二选一，而是从多份回答里选最好。还可能需要给每个回答独立打分，而不是只要赢家。

因此，第二组回答实验固定评委为 **Jev**，只改变评估方法。它比较的是方法，不是 Jev 与 GPT 谁更强。

### 4.2 数据长什么样？

使用 RewardBench 2，共 **1,865 条问题**。数据提供 `chosen` / `rejected` 优劣分组，**没有本实验使用的那种人工 1—5 分标准评分**。这里的 rating 指让 Jev 生成分数，再检查分数能否排对优劣，不是比较模型分数与人工分数的差距。

数据类别如下：

| 类别 | 主要检查什么 | 样本数 |
|---|---|---:|
| Factuality | 事实是否正确 | 475 |
| Focus | 是否聚焦问题 | 495 |
| Math | 数学回答质量 | 183 |
| Precise IF | 是否精确遵守要求 | 160 |
| Safety | 安全相关回答质量 | 450 |
| Ties | 多个好回答应如何并列 | 102 |

非 Ties 的 1,763 条，每条有一个标准好回答和三个较差回答。Ties 允许多个好回答，因此不能统一要求唯一赢家。

### 4.3 方法一：直接四选一（ranking）

把四份回答放在一起，问 Jev：“哪一份最好？”

正确回答的位置按样本变化，避免总放在 A。模型选中数据集标记的好回答，就计为正确。这种方法用于 1,763 条非 Ties 问题。

这里的 ranking 实际是选赢家，没有要求输出完整的第一到第四名。

### 4.4 方法二：给各回答打分（rating）

给每个候选定义同一套五档标准，从根本错误到完全正确。Jev 为各候选返回评分，再按分数比较好坏。这种方法用于全部 1,865 条。

同一问题的多个候选仍放在共同输入里，但分别提评分问题；所以这里的“逐个打分”并不意味着各候选完全看不到彼此。

例如，以下是教学示意：

| 候选 | 数据集标签 | Jev 分数 |
|---|---|---:|
| A | 好回答 | 2.8 |
| B | 较差回答 | 2.8 |
| C | 较差回答 | 1.2 |
| D | 较差回答 | 0.4 |

怎样给这次评分算成绩？有三种口径：

- **最高分命中（top-1）**：最高分里有好回答就算对。例子中 A 并列最高，所以算对。
- **严格排序**：好回答必须高于所有较差回答。A 与 B 打平，所以算错。
- **拆成两两比较**：分别比较 A 与 B、C、D。A 赢了两次，所以是 2/3。

同一组分数会得到不同成绩，不是计算矛盾，而是三个指标要求不同。尤其不能把拆开后得到的高两两比较准确率，冒充四选一准确率。

### 4.5 结果怎么样？

下面只在同一类别内比较两种方法：

| 类别 | 直接四选一 | 逐个打分：最高分命中 | 逐个打分：严格排序 |
|---|---:|---:|---:|
| 事实正确性 | 80.42% | 81.47% | 81.05% |
| 聚焦问题 | 93.54% | 87.88% | 87.68% |
| 数学 | 72.68% | 77.60% | 77.60% |
| 精确遵循要求 | 50.63% | 55.63% | 55.63% |
| 安全 | 87.78% | 66.44% | 66.44% |

最明显的是安全类别：直接选赢家为 87.78%，先打分再选只有 66.44%，相差 21.34 个百分点。数学则相反，打分后选择更好。

**这表明评估问题的设计会改变结果。** “比较谁更好”与“每份回答应打几分”不是完全相同的任务。实验显示了差异，但没有单独验证差异究竟来自评分尺度、提示措辞还是整体比较方式，需要后续控制变量实验才能解释原因。

精确遵循要求在两种方法中都相对薄弱，说明仅换一种评法没有消除这个短板。

直接四选一在 1,763 条非 Ties 样本上的总体准确率是 **82.47%**。rating 在全部 1,865 条上的 top-1 是 **77.91%**。二者的总体样本集合不同，不宜把这两个总数直接当成严格配对的差距；上表的同类别比较更清楚。

### 4.6 并列好回答怎么办？

Ties 的 102 条组成 51 组相关问题。除了要求好回答高于坏回答，还希望多个好回答之间的分差不要过大。

可以把它理解为：如果两个回答都正确，不能因为文风略有不同就拉开很大分差；真正应该拉开的是正确和错误回答之间的差距。

本轮 Ties 的 top-1 为 99.02%；使用包含间隔关系的专门聚合公式，得到 97.91%。**后者不是普通准确率，不能与四选一分数直接比较。** 本项目使用自定义 Jev 五档评分，结果也不是官方排行榜成绩。

两种完整方法的报告费用分别约为 $0.1610（四选一）与 $0.1980（打分）。

## 5. 把三组实验放在一起，应怎样理解？

| 实验发现 | 能得出的结论 | 不能直接推出的结论 |
|---|---|---|
| JudgeBench 上 GPT 更准，Jev 更便宜、更快 | 回答质量评估存在质量与成本的取舍 | Jev 在所有任务上都只是低价替代品 |
| APB 上 Jev 的过程判断领先 | 在这套轨迹、规则和预算下，Jev 更适合此任务 | 类型化决策模型普遍优于 LLM |
| APB 中 Jev 仍漏掉约 66% 错误 | 当前评委不足以独自承担错误拦截 | 排名第一就已经足够可靠 |
| RewardBench 2 两种评法差异明显 | 评分方法本身是实验设计的一部分 | 同一个模型存在一个与评法无关的固定能力分数 |

这三组实验不是把不同成绩拼成一个排行榜，而是在逐步回答三个问题：**模型会不会判断、判断方式会不会影响结果、到了真实 agent 过程里还能不能判断。**

如果目标是实际使用这些评委，下一步最需要验证的不是再多算一个总分，而是：在哪些错误上容易漏报，哪些情况需要人工或更强评委复审，以及把检查接入 agent 后是否真的提高任务成功率。这些问题，本轮静态评估还没有回答。
