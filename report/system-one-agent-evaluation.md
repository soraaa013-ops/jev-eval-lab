# 从 Jev 实验到通用 Agent 评估

更新：2026-11-16。本文补充同类模型对照与评估路线，不针对特定项目。
**证据分层：本仓库实测 / 外部论文或作者报告 / 建议开展的实验。新增模型尚未在本仓库运行。**

## 1. 应该怎样比较其他 System One 模型

此处的 System One 指读取状态、对预定义选项输出概率或分数的类型决策模型；
不能把所有小模型、奖励模型、非思考 LLM 自动视为同一种模型。
原实验中的 GPT-5 mini、Qwen chat judge 与 Skywork RM 是跨范式基线，尚不足以比较同类决策模型。

| 模型 / 路线 | 与 Jev 的主要差异 | 对 agent 评估的候选价值（研究建议） | 需要验证的边界 |
|---|---|---|---|
| Jev 1.14 | 托管类型决策 API；本仓库已有结果 | 作为无需自建推理服务的起始基线 | 复杂推理、精确指令、概率校准与服务漂移 |
| Laya | 开放编码器模型；英文根 checkpoint 421M / 默认 512 tokens；多语版本不同 | 短证据、固定原子问题的低资源评委；适合领域适配实验 | 不要把根模型、多语模型和专门微调版混同；长轨迹、相近候选与目标域校准需检验 |
| Kev | 开放 Qwen 系列决策模型，可训练、自托管，兼容 System One API | 在固定接口下比较本地部署、模型规模与定制训练收益 | 附带温度参数不保证跨域校准；需测目标硬件、实际轨迹长度与量化影响 |
| Clef / Clef-flash | Cloudflare 的开放决策模型，27B / 9B、64K 上下文；可托管 | 长证据与多问题评估的候选；比较精度与延迟 | 厂商速度与 benchmark 不能直接外推到本地或完整 agent 流程 |
| Decision 3.0（d3） | 开放多模态决策模型家族；d3 接收文本、图像、视频 | GUI / 浏览器 agent 的状态与截图评估候选 | 能接收截图不代表能可靠判断交互成功，须用环境状态验证 |
| 开放 LLM 的选项 logits / 简单决策头 | 不生成长文本，直接读取选项概率；可进一步微调 | 控制实验：收益究竟来自底座能力、决策训练还是服务形态 | 固定 prompt、候选顺序、上下文和校准方法后再比较 |

模型事实来自 [Laya 模型卡](https://huggingface.co/convaiinnovations/laya)、
[Kev 仓库](https://github.com/jaredpalmer/kev)、
[Clef 官方发布说明](https://developers.cloudflare.com/changelog/post/2026-10-01-clef-workers-ai/)、
[d3 模型卡](https://huggingface.co/vllm-sr/d3)。
这里列的是代表路线，不是完整目录或性能排名。自托管没有 API 账单也仍有 GPU、运维及排队成本。

两个外部研究提供了更有用的比较方向：

- **agent 决策点配对研究**：在 11 类决策点上比较 Jev 与 Laya，Jev 在 9 类显著领先，但零样本模型路由均未超过随机水平，RAG 相关性门控两者相当。这说明“通用快评委”的价值需要按决策点验证。作者还审计了评估流程：计入遗漏的预筛成本后，节省从 23.9% 降至 4.3%；单步门控正确率也不能当作端到端质量。结果仅适用于该研究版本与任务，不代表当前全部同类模型。[论文](https://arxiv.org/abs/2610.02267)
- **开放决策模型研究**：论文在 OpenDecisions 上报告 Gemma 4 31B 直接读 logits 的 Capability 为 79.6，Jev 为 80.1；微调后为 84.4。这里是该论文的复合 Capability 分数，不是准确率，更不是本仓库 JudgeBench 成绩。它支持把“开放底座直接读出”和“后训练决策头”纳入控制实验。[论文](https://arxiv.org/abs/2610.17205)

本仓库已完成 6 个 run、6,428 条判断。JudgeBench 中 Jev 78.14%、GPT-5 mini 85.71%，
Jev 费用约 1/42、p50 延迟约 1/32；这些是回答比较任务的测量，**尚未证明 agent 任务成功率提升**。
RewardBench 2 也仍是 Jev 自定义协议结果。[已有报告](report.md)

## 2. 对通用 Agent 评估的影响

核心变化是：可以尝试把大量局部语义检查做成便宜、结构化、可重复的过程信号。
它降低的首先是“获取评估信号的成本”，对最终任务质量的收益必须另行验证。

应分开两种角色：

1. **离线评委**：给历史轨迹打标签、定位失败、筛选需要人工复核的案例、支持版本回归；不会改变被评估 agent 的行为。
2. **在线控制器**：决定继续、重试、停止、换工具或升级模型。它会改变 agent 走过的路径，已经是系统的一部分；必须重跑任务评估收益。

| 评估层 | 适合交给类型决策模型的问题 | 真实证据与最终验证 | 主要指标 |
|---|---|---|---|
| 动作前 | 工具是否适用？前提是否满足？是否应请求澄清？ | 用户约束、当前状态、工具 schema；参数合法性优先用代码检查 | 不当动作漏检率、合法动作误拦率 |
| 动作后 | 工具返回是否支持预期结论？证据是否足够？ | 实际工具返回、状态 diff、可执行验证；不能只读 agent 的自述 | 虚假成功漏检率、证据支持判断准确率 |
| 过程 | 是否重复无效动作？发生偏离？失败是否已恢复？ | 轨迹窗口、累计状态、时间与预算；循环能用规则识别时直接用规则 | 故障检出率、首个有效告警步数、误报率 |
| 最终结果 | 开放语义要求是否满足？声明是否有证据？ | 测试、文件/数据库状态、任务完成条件及人工复核 | 真实任务成功率、约束违反率、成功误判率 |

例：agent 声称“文件已保存”。应先检查文件是否存在及内容是否合规；模型可以判断内容是否满足语义要求，
却不应凭“我已保存”的文字给成功标签。typed output 只保证结果形状，不保证结论真实。

推荐的混合结构是：**可执行验证 / 规则 → System One 原子语义检查 → 不确定或重要分歧交强模型 / 人工复核**。
“证据不足”应成为明确的输出选项；置信度不能替代证据。复杂长程因果、整体规划质量和新型任务，
仍需更强分析或人工；强模型本身也不能作为未经验证的真值。

不要把各步分数平均成任务成功率，也不要将它们的概率相乘：步骤之间相关，某个关键约束失败就可能使任务整体失败。
同时避免让 agent 与评委共享未经审计的推理自述，防止流畅解释替代客观执行证据。

## 3. 之后如何发展评估

以下为建议路线，尚未实施；按验收条件推进，不预设固定模型赢家。

### 阶段 A：先建立可验证的任务与轨迹数据

定义任务成功条件、关键约束和错误成本。记录 task_id、run_id、step_id、状态前后、动作、工具结果、
证据引用与最终产物；状态摘要也必须记录生成方式与成本。先选“工具结果是否被正确理解”和“是否虚假宣称成功”
两个易审核的切入点。可从 200–500 条分层轨迹做可行性试验，不能据此证明稀有失败足够安全。

人工独立标注并仲裁分歧，能用环境验证的部分保留验证结果。按任务族与时间划分训练、校准、锁定测试集；
同一任务的不同步骤、重试、改写与相邻变体必须在同一分组，防止泄漏。

交付物：带可回查证据的轨迹集、原子 rubric、标注一致性与未知标签比例。

### 阶段 B：先评估评委本身

保留规则、强 LLM judge 和现有 Jev；增加 Kev 与一个按需求选择的编码器或长上下文模型，
再扩展 Clef / d3。模型名单是实验选项，不要求一次部署全部。

冻结证据、问题、选项和版本；分别比较统一证据窗口与各模型原生上下文能力，报告截断和证据提取损失。
控制候选顺序、数量、语言、冗余、注入文本与轨迹长度。长度压缩产生的错误不能归咎为单纯模型能力。

除 accuracy 外，测失败漏检率、误报率、Brier / ECE、risk–coverage、跨任务漂移；按原始任务聚类 bootstrap。
同时测包含证据抽取、网络、批处理、重试在内的 p50/p95 和每条轨迹总费用。
只在校准集选阈值，并根据错误成本与置信区间确定可接受范围；没有通用的 0.8 或 0.95 阈值。

交付物：每一类检查的“误差—覆盖率—总成本”曲线，明确哪些检查值得自动化。

### 阶段 C：影子运行，验证整套评估系统

先并行打标签而不干预 agent，持续抽查高置信通过和模型分歧样本，检查是否漏掉真正失败。
若作为离线评估器替换已有流程，应检验与人工/环境结果的一致性，以及是否保留版本优劣排序。
减少人工工作量不能以漏掉回归为代价。

交付物：锁定测试集上的检测质量、审核工时、版本排名稳定性与域外失效清单。

### 阶段 D：若要在线控制，再做闭环消融

对照“原 agent”“加规则”“加 System One”“System One＋升级”四种流程；保持任务、预算、环境和随机条件尽可能配对，
并重复运行。旧轨迹只能评估当时的判断，无法证明另一条工具路径会成功；路由、重试或停止策略必须实际执行验证。

主指标为可验证任务成功率、关键约束违反率、过早停止率、每个成功任务的总费用、端到端 p95；
辅助看重试次数、升级率与人工工时。所有决策调用、证据提取、失败重试和复核成本都计入。
只有当成功质量满足预先定义的容忍范围且成本/延迟确有收益时才扩大使用；否则保留为离线诊断器。

### 阶段 E：数据稳定后才考虑专用训练

从真实错误、分歧与域外样本积累训练集；先比较 prompt、规则、温度校准与直接读 logits，
再尝试小模型微调或决策头。固定 holdout，防止训练到评委偏好却损害实际任务质量；保留外部环境验证与版本回归。

## 4. 对仓库下一阶段的具体含义

保留当前 pairwise benchmark 作为基础诊断；新增独立的轨迹数据契约和逐检查标签，不把轨迹强行转成 A/B 回答对。
在 adapter 层接入其他决策模型，在分析层补失败检测、风险覆盖与轨迹成本，在实验层分开 offline judge 与 online controller。
优先完成轨迹与真值、评委验证和影子评估，然后才研究在线路由与后训练。

一句话研究方向：**从“哪一个 judge 分数高”发展到“在可验证质量约束下，哪套评估与干预流程最划算”。**
