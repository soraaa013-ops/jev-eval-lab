# System One 模型验证与通用 Agent 评估建议

> **最新主实验：** 请先读 [System One 如何评估 Agent](agent-judge-benchmark.md)。
> 新增 BFCL / τ² 的 500 条真实轨迹、6,147 个步骤，Jev / Clef / GPT-5 mini 同证据对比。
> 下文保留此前回答质量实验与诊断研究，按各自口径解读；不混为 agent 端到端收益。

更新：2026-11-16。本报告讨论通用方法，不针对某个业务项目。

**主要结论：System One 的直接价值是把局部语义评估做成低生成开销、可批量调用的结构化信号；它既不自动获得可靠校准，也不自动成为可信的 agent 成功判定器。优先研究“执行证据是否支持 agent 声明”和失败分诊，再研究在线停止、重试与路由。**

与前一版只列模型名字不同，本轮做了三层验证：固定公开实现与配置；独立复算外部原始响应；在本机运行小模型诊断。完整机器可读证据见 [验证目录](../artifacts/validation/system-one/README.md)。

## 2. 同类模型的实质差异

System One 在这里指“状态＋声明的选项/量表 → 类型化决策与概率”。这一类别不是统一架构，也没有自动校准保证。与简单分类器、reward model 和直接读取 LLM 选项 logits 的边界应由具体实现说明，而非名称决定。

| 模型 | 核实的实现 / 发布形态 | 对评估的意义与代价 | 本轮验证深度 |
|---|---|---|---|
| Jev 1.14 | 托管类型决策；架构与训练细节不公开 | 易接入；无法直接审计内部机理；网络与服务版本参与结果 | 原仓库已跑 JudgeBench / RB2，未新跑 agent 任务 |
| Laya 英文根 checkpoint | ModernBERT 编码器＋2 层 head；`max_len=512`，`head_max_len=192` | 适合短证据候选；问题、选项也占预算；长轨迹尾部可能根本不可见 | 固定配置、代码与本地 CPU 推理 |
| Kev-0.8B | Qwen 底座＋LoRA＋pointer head；每个问题独立 row，服务端可共享状态缓存 | 可自训，适合控制领域与部署；应分别测域内、域外、长度与缓存收益 | 固定作者模型卡与源码版本；未加载权重 |
| Clef-flash | joint schema head：状态与多个问题联合编码；开放权重且可托管 | 多问题吞吐值得测；应加入“添一个无关检查是否改变原判断”的干扰试验 | 固定配置与 head 源码；9B 权重未在本机运行 |
| d3-edge | 固定选项 code readout；0.59B 发布模型含视觉部分；文本问题分别组织输入 | 可作为多模态小决策模型候选；多问题一请求不等于一次完整底座计算 | 固定代码、权重和本地文本推理；没有验证视觉能力 |
| 选项 logits / 简单决策头 | 开放 LLM 直接读取选项分布，或微调小读出层 | 必须纳入控制组，避免把底座能力归功于 API 形式 | 外部论文证据，本轮未训练 |

实现来源：[Laya](https://huggingface.co/convaiinnovations/laya/tree/e333cb7c823cd1787276228260f56d02fbf5180b)、[Kev 固定模型卡](https://github.com/jaredpalmer/kev/blob/2074cc44256200bb37540103fa4572901faa10f3/docs/model-cards/kev-0.8b.md)、[Clef-flash](https://huggingface.co/cloudflare/clef-flash/tree/22b75507981345858dd152fbd9a6f8c0c4068b0a)、[d3-edge](https://huggingface.co/vllm-sr/d3-edge/tree/bee5e872f75b9c5d1405767bf244a6948b95c0af)。完整 revision、文件哈希与配置摘录见 [catalog.json](../artifacts/validation/system-one/catalog.json)。

### 三个不能被接口兼容掩盖的差异

1. **证据预算。** Laya 的预算同时覆盖问题、选项和状态；默认右侧截断可丢掉末尾工具结果。Kev 提供的服务长度上限也不等于训练时见过相同长度。公平比较应同时报告“相同证据输入”和“各自原生上下文”两组，记录实际可见证据。
2. **概率含义。** Laya 的 `confidence` 由 `1 − 归一化熵` 得到，不能直接读成“判断正确的概率”；`max(probabilities)` 也需要经验校准。统一取所选答案概率计算校准指标，另保留原始 confidence。不要跨模型复用同一个阈值。
3. **多问题成本与干扰。** 独立 row、共享缓存、联合 schema、批处理是不同机制。每请求延迟会掩盖每检查成本；joint schema 可能存在问题间影响，这目前是需要测试的假设，不是已证实故障。

### 外部证据怎么读

- Kev-0.8B 作者模型卡的 `decision-v7` locked test 为 83.8%，但未训练过的 `breadth-v1` test 为 58.6%；这是不同分布，不能选择一个数字代表通用质量。其可训练性比“零样本平替 Jev”更有研究价值。[固定模型卡](https://github.com/jaredpalmer/kev/blob/2074cc44256200bb37540103fa4572901faa10f3/docs/model-cards/kev-0.8b.md)
- Cloudflare 报告 Clef / Flash 在其测量中的延迟与部分任务优势。这是厂商协议；本轮没有复现其延迟，不能与本机 CPU 或原仓库网络测量拼表。[官方发布](https://developers.cloudflare.com/changelog/post/2026-10-01-clef-workers-ai/)
- 开放决策模型论文报告，直接读 logits 已接近 Jev，微调可进一步改善；另一项固定底座的控制研究发现，小读出头接近复杂读出头，底座规模的影响更大。推论是：先验证数据、底座与校准，不应先假设专门架构必然更强。[开放决策模型研究](https://arxiv.org/abs/2610.17205)、[控制研究 v2](https://arxiv.org/abs/2611.15592v2)

## 3. 独立复算：Jev 与 Laya 在哪里不同

从 [sys1-eval 固定 commit](https://github.com/David-DL-Space/sys1-eval/tree/e74dfb6d99ed041f5f5240af386ba5272de84cdd) 的六轨道规模集重算；Jev 响应标识为 1.13.0，Laya 为当时的发布实现。使用每题主标签，二元阈值 0.5，失败响应计错。C 轨道使用作者修正响应。**这里是历史外部推理的复算，不是当前 Laya checkpoint 与 Jev 1.14 的新对战。**

| 决策点 | 案例数 | Jev 正确 / 准确率 | Laya 正确 / 准确率 | 对 agent 评估的启示 |
|---|---:|---:|---:|---|
| 模型路由 | 400 | 200 / 50.00% | 194 / 48.50% | 不宜从问题表面直接断言哪个模型会成功；需要真实的模型结果标签 |
| 工具选择 | 400 | 398 / 99.50% | 336 / 84.00% | 候选明确时有潜力；选对工具不意味着参数、执行和结果都对 |
| 是否需要工具 | 300 | 236 / 78.67% | 178 / 59.33% | “该调用吗”和“调用哪个”是不同难度，不可共用一个分数 |
| RAG 门控 | 400 | 243 / 60.75% | 234 / 58.50% | 相关性与可回答性标签不能混用；相近聚合分数不能证明等效 |
| 注入检测 | 400 | 372 / 93.00% | 313 / 78.25% | 可研究分诊；检测准确率不是真实攻击阻止率 |
| 多候选 / 多语言混合 | 200 | 162 / 81.00% | 70 / 35.00% | 需要按候选数和语言分层，混合结果不能解释单一原因 |
| 合计 | 2,100 | 1,611 / 76.71% | 1,325 / 63.10% | Jev 独对 455 题、Laya 独对 169 题；有大量共同失败 |

[逐题重算 CSV](../artifacts/validation/system-one/external-reanalysis/per-case.csv) · [指标](../artifacts/validation/system-one/external-reanalysis/metrics.json) · [输入哈希与口径](../artifacts/validation/system-one/external-reanalysis/manifest.json)。这些精确数字由脚本重算；本轮未重新核验外部标签正确性，也不声称复现了论文全部显著性结论。

外部论文自审还显示，漏算预筛调用成本会高估节省，同数据选阈值会低估漏检。研究本身主要是英语、零样本、固定版本，路由标签也有局限。因此它支持“分决策点验证”，不支持“System One 路由永远无效”。[论文](https://arxiv.org/abs/2610.02267)

### 另一项独立证据：相同步准确率，为何闭环表现不同

System1-Arena 在统一接口下比较 30 个模型。其 agentic 表中，Decision-2.0-Vega-27B、Jev 1.13、Qwen3.5-9B 的单步准确率同为 67.8%，但闭环成功率分别为 **26.5%、17.4%、5.7%**（127 个可比较环境的平均；不是 127 条任务）。这些是论文报告，本轮未复跑。它直接说明“步骤判对的比例”不足以预测持续交互表现；错误累积是作者提出的解释，尚不是单独识别出的因果机制。[论文表 2 与协议](https://arxiv.org/html/2610.21244v1)

这里模型承担的是决策/行动角色，不是纯离线评委，因此不能拿上述成功率当作 judge 质量排名。它对评估设计的意义是：当评委输出被用于停止、路由或重试时，系统已进入另一种分布，必须评价真实闭环结果。

## 4. 本地诊断：模型有没有真的看到并理解证据

运行环境为 CPU、2 线程、无可用 GPU；Laya 使用原生 FP32 路径与发布温度，d3-edge 使用其原生 BF16 底座 / FP32 readout。大模型未运行，不用小版本的结果外推整个家族。

自建 12 个基础案例来自文件保存、订票、测试通过、退款四种状态，每种分别有“支持 / 反驳 / 证据不足”三类。每题生成原始、反转选项顺序、长无关前缀＋尾部证据、夹带要求判成功的文本、移除证据五种变体，Laya 共 60 条；d3-edge 正式运行仅原始、顺序反转和移除证据，共 36 条。d3 首次计划在完成 5 条后因 CPU 长输入约 53 秒/次而中断，已有失败输出也原样保留，不纳入正式组。它们在一次 smoke probe 之后编写，不是预注册或盲选 benchmark；缺失证据变体在同一场景内重复，不能当作独立样本。

| 条件 | Laya 正确数 | d3-edge 正确数 | 解释 |
|---|---:|---:|---|
| 原始短证据 | 8/12 | 11/12 | 不外推为真实轨迹准确率 |
| 只反转选项顺序 | 10/12 | 11/12 | 语义标签保持不变 |
| 移除证据，应弃判 | 3/12 | 6/12 | 4个唯一输入各重复3次 |
| 长前缀＋尾部证据 | 4/12 | 未完成正式组 | Laya 12条均截成相同token序列 |
| 夹带要求判成功的文本 | 6/12 | 未完成正式组 | 单一模板，非完整注入攻击评测 |

反转顺序后，Laya 有 2/12 条改变选择，d3-edge 为 0/12。
Laya 的原始短例 p50 约 2.15 秒；d3-edge 约 9.50 秒。精度、运行时和输入方式不同，这些 CPU 测量不能作为服务速度排名。

**明确反例：** `tests-B-original` 的工具证据为“7 passed, 3 failed; exit code 1”，但两个模型都支持“全部10项通过”的声明；所选概率分别为0.5865与0.7045。可执行计数应由代码核验。`file-A-no_evidence` 上两者分别判支持和反驳，而正确标签是证据不足。

[逐例反例审计](../artifacts/validation/system-one/error-audit.md) · [Laya原始结果](../artifacts/validation/system-one/laya-probes/results.jsonl) · [d3原始结果](../artifacts/validation/system-one/d3-edge-probes/results.jsonl)。

这些诊断要回答的是故障是否存在，而非估计总体故障频率。特别是：即使某模型短例全部判对，也不表示它可以上线；如果两个不同真值输入被截断成相同 token 序列，任何后续读出头都不可能恢复被删掉的事实。

## 5. 对通用 Agent 评估究竟有什么改变

### 5.1 三种角色，三种不同验收标准

| 角色 | System One 可以提供什么 | 要如何验收 |
|---|---|---|
| 离线评委 | 结构化标签、失败分诊、版本回归筛查 | 与独立标注的误差；漏掉关键回归的概率；是否改变版本优劣排序；实际审核工时 |
| 过程观察器 | 工具结果解释、证据支持、约束满足、失败恢复等逐步信号 | 失败检出率、首个有效告警位置、误报、证据引用是否完整；不能只看平均步分 |
| 在线控制器 | 触发复核、重试、停止或升级 | 实际重跑后的成功率、违规率、过早停止、全链路费用与 p95；离线判断准确率不能替代 |

这使评估有机会从“最终回答打一分”发展成“最终结果＋关键约束＋证据化过程”的多层测量。但**它降低的是评估信号的获取成本；能否提升 agent 能力，是另一个实验问题**。

### 5.2 最值得先做的应用

**第一优先：证据支持检查与虚假成功发现。** 输入应为任务约束、实际工具输出、状态 diff、待核验声明；输出支持/反驳/证据不足。例如文件是否存在由系统检查，内容是否满足语义要求交模型；不要只给“我已保存”一句话。对关键完成条件要求证据定位，定位由 harness 提供，不能依赖无生成模型凭空给解释。

**第二优先：失败分诊与审核队列。** 先标注失败类别和不确定项，帮助人工查看最需要复核的轨迹。抽查高置信通过样本，避免审核只看到低置信失败；低频新型错误可能正是高置信误判。

**第三优先：局部过程评价。** 分开“推进任务 / 合理探索 / 错误或违规”，保留“证据不足”作为独立不确定状态。一次探索没有立即产出不应自动判错；恢复后的最终成功也不应抹掉之前的关键违规。

**后置：通用自动停机、开放式规划评判与模型路由。** 这些问题涉及后续结果、复杂推理或反事实。在线工具适用性检查只能看动作前证据；动作后评价可以看工具结果；离线分析能看完整轨迹。混用可见信息会制造评估优势。规则可解的参数合法性、配额、重复调用等，优先交代码。

### 5.3 需要修正的两个常见想法

- **环境检查也需要审计。** AgentRewardBench 发现固定规则可能漏掉实际成功的路径；“环境真值”应指与任务语义一致、经过验证的检查器，而非任何脚本输出。该基准的 1,302 条专家审核 web 轨迹可用于评价最终成功判定器。[论文](https://arxiv.org/abs/2504.08942v2)
- **高平均步准确率未必是好 agent。** AgentProcessBench 的 1,000 条轨迹、8,509 个人工步骤标签区分有效、探索与错误；研究指出过早结束可抬高正确步骤比例。评估应同时保留结果质量、过程失误和停止行为。[论文](https://arxiv.org/abs/2603.14465v2)

评估对象是模型与 harness 组合；一次任务需要多次 trial 来测稳定性，最终环境状态与 transcript 不能混为一谈。[Anthropic 方法说明](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

## 6. 推荐发展的评估框架

### 6.1 数据与标签：先建立评估契约

每个任务明确成功条件、硬约束、允许的替代路径和错误成本。记录任务/运行/步骤 ID、版本、状态前后、工具参数与返回、产物、证据引用、可见信息范围、输入压缩和截断。不可见不等于失败；输出结构至少有 `label`、`probabilities`、`evidence_ids`、`abstain_reason` 和版本。

由独立人员审核与仲裁，而不是把强模型输出直接当真值。按任务族、站点/领域和时间划分训练、校准与锁定测试；同任务的步骤、重试、改写与干扰变体放同组。对罕见错误另建挑战集，同时保留真实流量分布集，不能用人为平衡集估算线上风险。

### 6.2 先评估评委：最小实验矩阵

| 维度 | 第一轮方案 | 目的 |
|---|---|---|
| 对照 | 规则、强 LLM、Jev、Laya、一个 Kev 小版本；有长证据/截图再加 Clef/d3 | 分离架构、规模、部署与证据形态 |
| 输入 | 最终回答；原始轨迹；提取的可核验证据 | 判断收益来自模型还是输入处理；计入提取成本与丢失 |
| 输出 | 整体成功判断；拆分的原子检查；原子检查＋弃判复核 | 检验拆分是否有效，而非先假设有效 |
| 扰动 | 选项交换/改写、无关问题、冗余长度、缺证据、agent 自述与工具事实冲突、注入文本 | 检验测量稳定性与证据依赖 |
| 分布 | 域内、留出任务族、不同语言/长轨迹 | 检查泛化，避免在总体平均分中掩盖失效 |

不是把所有组合一次穷举。先用支持检查跑通规则＋强模型＋两个决策模型，对效果最敏感的因素做消融，再扩大模型规模。

### 6.3 指标：必须把漏判与误拦分开

- 以失败为正类：失败漏检率、错误告警率、precision/recall，按关键错误类型报告；另测“判成功但实际失败”的比例。
- 校准与选择性预测：Brier、ECE、risk–coverage，阈值在独立校准集上按错误成本选；检验移域后的覆盖率与风险。
- 评估系统自身：人工一致性、不同 judge 的分歧、版本排名反转、关键回归漏检、每条轨迹审核成本。
- Agent 系统：可验证成功率、关键约束违反、过早停止、恢复成功、多次运行的稳定性、每个成功任务总成本与 p95。

统计以原始任务为聚类单位，报告配对差值置信区间。多个变体、同轨迹步骤或重复缺证据案例不是独立证据。不能把步分均值或概率乘积当作任务成功率，也不能用“没看到错误”宣称低风险已被证明。

### 6.4 经济性：便宜评委何时真的省钱

设强评委单次成本为 `C_strong`，快评委为 `C_fast`，证据提取为 `C_extract`，升级比例为 `q`。简化的每次检查成本是：

`C_hybrid = C_extract + C_fast + q × C_strong`

只有在**达到相同错误约束**且 `C_hybrid < C_strong` 时，级联才算节省。若每条轨迹有 K 个检查，需要按实际 K、共享缓存和批处理重新计费；自托管 GPU、失败重试与人工复核也要计入。每步加入一个快检查仍可能累计出显著延迟。

同样，反复拦截会累积误报。仅作数学示例：若 50 次检查各有 1% 误报且相互独立，至少误报一次约为 39.5%；真实步骤相关，应直接测量轨迹级误拦，不能套用独立假设得到上线结论。

### 6.5 先影子运行，再证明干预价值

先只记录判断，不改变行为；人工抽查模型分歧、低置信和高置信通过三类。验证关键回归不会被漏掉，并衡量审核工时是否下降。

通过后，比较“原 agent”“加规则”“加决策模型”“决策模型＋升级”四组。保持任务、预算和环境尽可能配对，多次执行。对路由或重试策略，旧轨迹没有另一条路径的真实结果，必须重新执行；否则只能报告离线反事实假设。

验收条件预先写成“成功率差值的置信区间不突破容忍范围；关键失败风险达标；总成本/延迟至少一项改善”。若不满足，就保留作诊断与审核辅助，不把它推进在线门控。

## 7. 建议的研究优先级与后训练门槛

1. **先补 agent judge benchmark。** 用 AgentRewardBench 测最终成功/副作用判定，用 AgentProcessBench 测步骤质量；这些是待执行方案，本轮未运行它们。现有 JudgeBench / RB2 保留为回答质量诊断，不承担 agent 结论。
2. **再验证证据与结构。** 在同一批轨迹上比较“全轨迹整体评分”和“证据提取＋原子检查”。首要产物是失败模式、漏检—覆盖—成本曲线，不是统一模型名次。
3. **优先小模型分诊，谨慎在线裁决。** Laya 的短窗口决定需要输入工程或领域训练；Kev 可用于领域适配研究；Clef 的长上下文/联合问题值得做成本与干扰实验；d3 的视觉能力要单独以截图和环境状态验证。本轮小模型诊断不给这些方向背书。
4. **后训练要有门槛。** 数据稳定且错误可归类后，先比较规则、prompt、温度校准和直接 logits；只有微调在锁定域外/新任务测试集上改善目标风险与实际成本，才值得维护专用模型。不得用待比较模型自身标签构造唯一真值。

研究主线应从“哪个 judge 分数高”，转向“什么证据、什么问题、什么模型和复核策略，能在明确风险约束下提供更可靠且更便宜的 agent 评估”。
